\section{引言}

智能体在调用工具完成任务时，参数会被传给外部服务。一个容易被忽视的问题是：智能体可能正确完成了任务，却在可选参数中填入了当前操作并不需要的敏感信息。例如，取消订单只需订单编号，但智能体可能同时把出生日期和支付卡号也传了过去——订单照常取消，敏感信息却到达了本不需要它的服务。这种披露不是攻击者诱导的结果，也不影响任务完成，但它超出了当前操作的信息用途。

本文将这种现象称为\textbf{冗余参数泄露}（Redundant Parameter Leakage, RPL）。它与提示注入攻击\citep{debenedetti2024agentdojo}的区别在于：后者是外部攻击者试图改变智能体行为，前者发生在正常的、功能正确的执行过程中。它也不是参数错误——工具选择、必填参数和最终状态都可以是对的，问题只在于调用中多了几个本可删掉的敏感参数。

判断哪些信息可以披露，不能只看字段是否敏感，还要看它流向谁、出于什么目的\citep{nissenbaum2004contextual}。同一个电话号码，通知工具可能需要，查询工具则不需要。已有研究在对话场景中考察语言模型的隐私判断能力\citep{mireshghallah2024confaide,shao2024privacylens}，但模型能否在工具调用中遵守同样的约束，仍缺乏专门的评测数据。\ToolPrivacyBench 是与本工作最接近的研究：它将用途约束引入工具轨迹审计，发现任务完成与隐私合规是两个独立的维度\citep{hu2026toolprivacybench}。后续工作进一步从信息流追踪\citep{ngong2026agentscope}和动态工具生态\citep{wang2025privacyinaction}等角度扩展了智能体隐私的边界。这些工作表明，只检查最终回答或任务完成情况，不足以发现执行过程中的参数级泄露。

然而，把现有工具调用任务转化为 RPL 评测数据存在实际困难。$\tau$-bench、BFCL、API-Bank 和 AppWorld 四个基准各自保存参考调用的方式不同：有的是任务动作，有的是多轮对话，有的是逐条 API 记录，有的是通过环境验证的执行日志。它们对用户身份、工具可见范围和轨迹完整性的表达也各不相同。如果转换时直接把这些记录都当作标准答案，不仅会丢掉来源信息，还可能把一条参考路径误当成唯一解或最短路径。

本文的做法是保留上游参考调用的全部参数不变，在此基础上构造一个增加了可选敏感字段的对照版本。如图\ref{fig:rpl-motivation}所示，两条调用使用同一工具和同一必填参数，唯一区别是后者多了若干可选的敏感字段。这样，隐私泄露就与工具选择错误、必填参数缺失等功能问题分离开来，差异精确落在多出来的参数上。本文不宣称这一数据已经达到人工业务授权意义上的最终标准，而是提供一个透明、保守、可重复运行的参数级隐私评测基础。

本文的主要贡献如下：

\begin{enumerate}
  \item 提出冗余参数泄露的配对构造方法：每步提供不泄露和泄露两个调用版本，差异只落在多出的可选敏感参数上，可以精确计算和校验。
  \item 分析 $\tau$-bench、BFCL、API-Bank 与 AppWorld 的原始任务结构和验证机制，设计保留来源差异的适配与审计流程。
  \item 构建包含 328 条任务的 RPL 数据，逐条提供工具定义、用户档案、配对调用和来源证据，并分层报告结构校验、源重放、环境执行和最终状态验证的结果。
  \item 从四个来源分层抽取 80 条参数授权关系进行人工复核，人工判断与确定性标签在 78 条样本上保持一致。
\end{enumerate}
