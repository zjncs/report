\section{文献综述}

本文的问题位于两条研究脉络的交汇处：一条脉络关心智能体能否正确调用工具并完成多步任务，另一条脉络关心信息披露在特定情境、用途和接收方之间是否合宜。前者为本文提供了可执行的任务骨架与功能验证依据，后者则决定了为什么“任务完成”不等于“披露恰当”。因此，本节不仅回顾相关工作，也说明这些工作如何逐步引出本文的数据表示与构造原则。

\subsection{从函数匹配到可执行任务}

早期工具调用评测主要检查模型能否根据自然语言选择函数，并生成符合模式的参数。API-Bank 将这一过程拆分为工具检索、调用规划与 API 执行，使工具能力不再只是一次静态函数匹配\citep{li2023apibank}。BFCL 进一步扩展了函数语言、并行调用和多轮任务，并在多轮部分结合状态与响应检查来判断任务是否完成\citep{patil2025bfcl}。这类工作说明，工具调用的正确性需要同时考虑工具选择、参数结构和调用顺序。

随着评测对象从单次函数扩展到交互式智能体，正确性的判据也从“是否复现某个调用”转向“是否产生预期的环境结果”。$\tau$-bench 把智能体置于航空与零售客服场景，要求其在与模拟用户交流的同时操作状态化数据库并遵守业务政策\citep{yao2025taubench}。AppWorld 则在可重置的多应用环境中，通过程序化测试判定跨应用任务的完成情况\citep{trivedi2024appworld}。ToolSandbox 对有状态工具、隐式依赖与多条可行轨迹的强调，同样表明单一字符串答案不足以概括真实的任务成功\citep{lu2025toolsandbox}。

本文采用的四个源基准提供了可追溯的参考调用，但它们的证据强度并不相同：有的保存目标动作，有的保存多轮参考调用，有的记录单次 API 请求—结果，有的则由最终状态评测器判定任务。这一差异直接引出本文的第一个设计要求：统一的输出格式不应抹平源语义，因此需要为不同基准分别解析 reference、工具可见性、用户状态和验证证据。

\subsection{情境与用途约束下的隐私}

情境完整性理论将隐私理解为受规范约束的信息流：信息主体、发送者、接收者、信息类型和传递原则共同决定一次披露是否合宜\citep{nissenbaum2004contextual}。电话号码或支付信息并非在所有场景中都应被隐藏；关键在于当前任务、接收方和用途是否为该信息的传递提供了充分理由。CONFAIDE 将这一思路转化为语言模型的情境化信息分享判断，说明脱离情境的“敏感/不敏感”分类无法充分表达隐私边界\citep{mireshghallah2024confaide}。

对工具调用而言，接收者和用途已经具体化为工具及其职责。同一个用户字段可能是某个操作的必要输入，却与另一个操作毫无关系。因此，本文不将授权简化为字段的全局属性，而将判定单元设定为特定任务中的“敏感字段—工具”关系。这一表示承接了用途约束的理论要求，但理论本身并不直接给出自动标注算法；具体授权仍需要结合工具用途、参数模式与任务证据判断。

\subsection{从隐私判断到行动与轨迹}

模型能够识别隐私规范，并不意味着它在行动时会遵守该规范。PrivacyLens 将隐私评测从抽象判断延伸到具体行动，发现模型的规范认知与实际选择之间可能存在显著差距\citep{shao2024privacylens}。Privacy in Action 进一步把观察对象放入 MCP 和 A2A 等动态工具环境，强调应当检查智能体真正发出的请求，而不是只询问它“应该怎么做”\citep{wang2025privacyinaction}。

当任务包含多次工具交互时，最终回复也不足以代表完整隐私结果。AgentSCOPE 使用 Privacy Flow Graph 追踪信息在用户、智能体、工具和接收者之间的传播，表明即使最终回复没有显示敏感值，中间工具请求仍可能已经越过了信息边界\citep{ngong2026agentscope}。本文不试图复制完整的信息流图，而是选择其中一个可精确观察的边界：智能体发往工具的参数。这一选择引出了两项设计：保留完整参考轨迹，以呈现字段在不同步骤中的用途变化；同时在同一步内对照功能参考调用与泄露调用，将差异限定在新增敏感参数上。

\subsection{ToolPrivacyBench}

\ToolPrivacyBench 是本文数据改编思路的直接来源。该工作以 purpose-bound 和 need-to-know 为核心，为每条任务建立私有信息原子与字段—工具授权关系，再利用后端审计日志检查智能体是否将禁止披露的信息传给工具\citep{hu2026toolprivacybench}。其 2{,}150 条任务中，1{,}000 条改编自 BFCL、AppWorld、$\tau$-bench 和 API-Bank，表明现有功能基准可以作为隐私评测的工作流骨架。该工作还以源调用数、不同工具数、私有信息量和 forbidden 机会等条件筛选任务，并将任务成功与隐私披露分开计量。

本文直接借鉴了其中四项方法思路：从多步公开任务中筛选适合的工作流，把分散的敏感事实组织为任务实体，在字段与工具之间表示用途约束，以及将功能正确性与隐私检查分开。本文采用的“至少四次源调用、两个不同工具、四个敏感字段和二十个 forbidden 字段—工具组合”也是对该筛选框架的任务化改编，而非由本文数据分布自然推导得出的统计阈值。

两项工作的目标并不完全相同。\ToolPrivacyBench 主要观察智能体在实际执行中的过度披露，并以工具用途为先的语义判断和人工复核支持授权标注；其对 215 条任务、21{,}994 个字段—工具关系的双人复核报告了 93.1\% 原始一致率和 $0.86$ 的 Cohen's $\kappa$\citep{hu2026toolprivacybench}。本文的重点则是可复现的数据构造：保留上游 reference，并为通过 carrier 筛选的步骤生成仅增加敏感可选参数的配对调用。当前的 allowed/forbidden 标签是基于来源参数证据的确定性基线，因而具有可重放性，但不等价于 \ToolPrivacyBench 的人工业务授权标准。

\subsection{相邻风险与本文边界}

智能体隐私并非单一问题。TOP-Bench 关心多个单独看似无害的工具结果被组合后推导出敏感信息，其核心是组合推断，而不是已知敏感值的直接传递\citep{qiao2025topbench}。AgentDojo 等工作考察提示注入攻击下的数据泄露与工具滥用\citep{debenedetti2024agentdojo}；POLAR-Bench 则将隐私与效用的张力放入第三方主动探测场景\citep{zheng2026polarbench}。这些工作分别对应组合推断、对抗诱导和主动探测等威胁模型。本文不以这些威胁为前提，而专注正常任务中的直接冗余披露：工具调用在保留必要功能参数的同时，又携带了当前步骤不需要的敏感可选参数。

综合上述文献，本文形成四项相互关联的设计原则。第一，授权应在具体任务的字段—工具关系上表达，而不是把敏感性当作字段的全局属性。第二，隐私评测应落在真正执行的工具参数上，因而需要参数级的功能—泄露配对。第三，多步任务的信息必要性可能随步骤变化，数据应保留完整 reference 与步骤边界。第四，不同源基准对“正确调用”提供的证据强度不同，数据构造应将来源保真、模式校验、环境执行和最终状态验证分层记录。下一节将回到四个源基准的原始任务与评测机制，说明这些原则如何落实为具体的适配和验证方法。
